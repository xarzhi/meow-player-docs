# 性能与资源占用

播放器这种「开着就不关」的软件，占多少内存、会不会越用越涨，比功能多少更要紧。这一页把实测数据和做过的取舍都写出来。

## 实测数据

| 项目 | 数值 |
| --- | --- |
| 安装包体积 | **约 57 MB**（`MeowPlayer_v0.2.0_setup.exe`） |
| 主程序 exe | **约 32 MB**（Release 构建，含图标与版本资源） |
| 卸载器 | 约 9 MB（用 `opt-level="z"` + fat LTO + strip 单独构建的） |
| 运行内存（Release，空闲） | **约 50 MB** |
| 进程数 | **1 个**（没有 Electron 那种「主进程 + 渲染进程 + GPU 进程」） |
| 运行时依赖 | **无**（不需要装 WebView2、不需要 .NET） |

> Debug 构建的内存会明显高一些（开发时看到 170MB 左右是正常的），发布版请用 Release。

## 为什么体积和内存能压下来

**没有 WebView**。界面是 GPUI 直接用 GPU 绘制的，不需要带一个 Chromium / WebView2 运行时 —— 这也是为什么安装包能只有 57MB、启动只需要一个进程。

**封面按需解码 + 分档缓存**。缩略图不是一次性全解出来，而是访问到才在后台线程解，并且**按显示尺寸分档缓存**（64px 一档、最低 96px）—— 底部播放条那张 48px 的唱片不会去用全屏的 680px 大图，取图尺寸贴着显示尺寸走。

**频谱不额外分配**。取样只用一条定长环形缓冲（8192 个单声道样点，约 0.19 秒），FFT 是手写的 1024 点、每帧复用窗口数组 —— 不会为这个功能引入 FFT 库，也不会每帧堆一堆临时对象。

**该回收的当帧回收**。这个项目踩过一个很典型的坑，值得记一笔：

> 全屏播放时黑胶唱片每帧都要转出一个新贴图（464×464，约 860KB）。原来的释放逻辑写在主界面的渲染里，而全屏页不走那条路 —— 于是**每帧转出来的旧贴图只进不出**，60fps 下大约 50MB/s，几分钟就能吃掉几个 G。
>
> 修法是：把「回收不再使用的图」这一步挪到**两条渲染路径都会经过**的地方（`window_overlays`），保证旧贴图当帧就被摘掉。修复后内存稳定在一个数量级，不再随播放时间上涨。

## 高频路径上做过的优化

- **取样环形缓冲不再每个样点搬一次**。原来每来一个样点就把整个缓冲往前挪（44.1kHz 下约 1.4GB/s 的内存搬运）；改成攒够 1024 个才挪一次，摊下来是 O(1)；
- **封面只在换歌时查一次**。迷你播放器开着时，状态每 16ms 推一次；早期实现每次推送都去封面缓存里按「路径 + 尺寸」查一遍，白白做字符串构造和查表。现在只在路径变化（或上次没解出来）时才查；
- **贴图按显示尺寸分档**。唱片贴图按 64px 分档生成并缓存，拖窗口改尺寸不会每一档都重新生成；
- **动画只在该播的时候挂**。gpui 的元素重新挂载时动画会从头播一遍，所以项目里普遍用「截止时间 / 序号」把动画限制在真正需要的那段时间内，避免空转重画；
- **不给整窗面板挂 opacity**。在 gpui 里给一个元素加透明度会让它被合成到一张全窗口的离屏层，全屏页进出场因此只动高度、不动透明度。

## 流畅度

- 全屏播放页在**播放时**按帧驱动（`request_animation_frame`），逐字歌词、唱片旋转、频谱都跑在这条节拍上；
- 迷你播放器用自己的 16ms 节拍推状态（主窗口收起来之后它不再渲染，所以这条节拍是必要的 —— 否则歌词和进度会停在开窗那一刻）；
- 播放条上那张小唱片的旋转用的是 **20fps** 的慢节拍：40 秒转一圈大约 9°/秒，20fps 已经足够顺，不值得为此每帧重绘整个窗口；
- 想要看实际帧率，启动时加环境变量 `MEOW_FPS=1`，程序会每 60 帧在控制台打一行。

## 体积还想再小？

- 安装器与主程序都用 Release 构建（`strip = true` + `lto = "thin"`）；
- 卸载器单独用 `profile.small`（`opt-level = "z"` + fat LTO + strip）；
- 这些都是 `Cargo.toml` 里的 profile 设置，改一行就能在「体积」和「编译时间」之间重新取舍。
